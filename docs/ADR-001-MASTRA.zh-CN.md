# ADR-001：采用 Mastra 构建 Milo V1.0

- 状态：已决定
- 日期：2026-11-16
- 范围：八周 V1.0 的 Agent 运行、工作流与存储架构
- 实现状态（2026-11-16）：基础工程与依赖锁文件已建立，已接入常驻服务、PostgreSQL 和空注册表；本文三项业务验证仍未执行。当前锁定版本用于基础开发，业务恢复边界须在 W1 验证后验收。见 [开发说明](DEVELOPMENT.zh-CN.md)。

## 背景

Milo 首版包含持仓分析、公司研究、投资档案与按需复查，需要接入投资记账本 MCP、引用研究证据、等待用户确认，并在长任务中断后恢复。

用户已确定采用 Mastra。选择依据是这些产品能力的集成需求，不以已有项目使用 Pi 作为默认沿用理由。V1 不要求每日复盘、固定日频调度或每日推送。

## 决定

采用 **Next.js + TypeScript、常驻 Node.js Mastra 服务、PostgreSQL**，前端、后端和 Agent 保持同仓库。

```text
Next.js 页面与业务 API → 常驻 Mastra 服务
                         ├─ Workflows / 步骤内 Agent → MCP、资料检索与计算工具
                         └─ PostgreSQL 运行存储与 Milo 业务表
```

- Next.js 负责工作台、访问控制、任务发起和进度展示；页面请求断开不承担任务终止语义。
- 常驻 Node.js 服务执行 Mastra 工作流并运行后台 worker；不把长任务生命周期绑定到浏览器连接。
- 优先采用基础 Workflows 编排明确步骤，在研究计划、资料综合等步骤中调用 Agent。
- PostgreSQL 保存 Mastra 运行状态及独立的 Milo 业务数据；两者区分表或命名空间。
- MCP 用于读取账本提供的账户事实。缺失字段明确标记，不由模型推造成交、快照或收益。
- 研究证据索引、金额计算、引用校验、用户确认与业务权限由 Milo 实现，通过工具接入工作流。

## 会话、记忆与正式档案

Mastra Memory 用于对话上下文和必要的会话记忆，不作为正式投资理由档案或账户事实来源。

正式投资理由、用户约束和复查提案保存在 Milo 的版本化业务表中，记录用户或模型来源、创建时间、确认时间与关联证据。模型草稿经用户确认才成为当前版本；聊天摘要不能自动升级为用户立场或已确认事实。

## 持久运行与发布边界

- 基础工作流恢复必须配置持久 storage，并按所选版本启动 `startWorkers` 对应的后台 worker；仅开启流式输出或保存聊天记录不足以证明崩溃恢复。
- 用户确认使用工作流暂停/恢复机制，并持久保存业务运行 ID、待确认内容版本及授权范围。暂停状态跨进程重启后仍应可确认并继续。
- 工作流检查点负责运行续接；被中断、尚未提交的步骤可能重跑。工具调用和外部写入不能假定“恰好执行一次”。
- Milo 自行定义业务幂等键，包含用户/账户范围、工作流版本、源数据快照及输入版本。重复投递与恢复使用同一业务身份；新输入或显式新修订保留历史记录。
- 报告发布通过数据库唯一约束和事务去重；正式档案更新还需校验用户确认与当前版本，不能仅凭工作流完成事件写入。
- 取消和发布争用同一业务状态的原子边界；取消已生效后，迟到或重跑的执行不得发布产物。供应商请求已产生的费用不因取消而自动撤销。
- Mastra 提供的租约与重试机制不替代业务权限、幂等发布、并发版本冲突和取消竞争处理。

## 评测与观测

使用 Mastra evals 与 tracing 接入测试和诊断，但投研评测集、数值标准答案、引用支持度及人工抽检规则由 Milo 定义。

记录业务运行 ID、工作流/模型/提示词版本、步骤状态、工具调用摘要、token、耗时和费用口径；区分成功、部分完成、失败与取消。Trace 是诊断记录，不替代账户快照、原始证据或正式投资档案。

## 不作为 V1 前提的能力

- 不默认叠加 Pi 或 pg-boss 作为第二套 Agent/工作流编排层，避免同一任务存在两套状态与恢复责任。
- 不以 beta Durable Agents 为 V1 前提；其与基础 Workflows 恢复属于不同能力边界。
- 不以 Temporal 或 Inngest 为 V1 前提；仅在基础方案无法满足实测需求时单独形成新决策。
- 不为选型额外引入多 Agent 辩论、自动交易或固定日频任务。

## W1 前 1–2 天验证

以下三项均**尚未执行**。先完成可复现的最小验证，再锁定 Mastra、模型适配器、MCP 和存储依赖版本及配置。

| 验证 | 执行方式 | 通过标准 |
| --- | --- | --- |
| 真实 MCP 接入 | 使用实际账本连接，列出可用能力并调用一个已授权只读工具，经过 Mastra 工具与工作流返回结果 | 真实请求成功；保留脱敏调用证据与字段映射；数据时点和缺失能力可见；结果可追溯至原响应，模型未补造字段 |
| 暂停后重启再确认 | 工作流生成待确认提案后暂停，重启 Node.js 服务，再由用户确认该版本 | 原业务运行、暂停点与提案版本可重新获取；未确认不继续；确认后续接成功；重复确认不重复更新正式档案 |
| 强杀后恢复且不重复发布 | 在长步骤执行或发布前强杀进程，重新启动服务和 worker，并重复投递同一业务请求 | 原业务运行可按持久状态恢复或有界重试并完成；已提交产物不重复写入；同一输入最终仅发布一份对应报告，尝试与恢复过程可追踪 |

每项保存依赖锁定清单、必要配置、脱敏日志及结果。任何一项未通过，应先定位存储、worker、步骤重试或业务事务问题；不得用前端刷新可继续查看，替代进程崩溃恢复的验收，也不自动追加第二编排框架掩盖失败。
