# Milo V1.0：个人投资助手

> Your personal investment assistant.

版本：规划草案 v1.1（Mastra 方案）

更新：2026-11-16

周期：8 周开发量

现状：仓库已建立基础工程，包括 Web 空态、常驻 Mastra 服务、PostgreSQL、共享包和 Ultracite；本文中的投资业务功能及业务验收仍待实现。基础工程使用方式见 [开发说明](DEVELOPMENT.zh-CN.md)。

## 1. 版本目标

让个人投资者能够基于自己的真实持仓，研究公司、保存投资理由，并在需要时复查判断。

核心流程：

**看懂持仓 → 研究与比较标的 → 记录投资理由 → 仓位变化试算 → 实际操作后按需复盘 / 用新证据复查原判断。**

用户通常不需要每日操作，因此本版取消每日复盘、每日推送和固定日频任务。研究、试算、操作复盘和理由复查由用户发起；手动同步发现新成交时，可以提示补记理由与进入复盘。

## 2. 已确定的要求与规划假设

已确定：
- 名称 Milo，介绍 Your personal investment assistant.
- 首个大版本同时包含持仓分析与公司研究。
- 账户事实以投资记账本 MCP 为来源，缺失能力明确标记；前端、后端及 Agent 同仓库。
- 本次按八周开发量规划，包含可演示交付与简历所需的验证材料。
- 按需复盘，适配非日内、低频操作的投资习惯。
- Agent 框架确定采用 Mastra，整体采用 Next.js + TypeScript + 常驻 Node.js Mastra 服务 + PostgreSQL。

为估算采用的假设：
- 单人每周约 30 小时，合计约 240 小时，包含测试、集成与修复。投入减少时应顺延日历时间。
- 单用户私有使用优先；公开演示使用合成数据。
- 持仓展示范围由 MCP 能力决定；深度公司研究先完整验收一个市场、约 6–10 家代表性公司。
- 至少一种模型服务和一条稳定的财报/公告获取路径可用。第一周验证费用、额度、文档可用性与认证。
- 框架选型已确定；基础依赖已安装并固定版本，运行环境和业务恢复配置仍需第一周验证后验收。

## 3. 竞品启示

完整调研见 [竞品与开源方案调研](COMPETITORS.zh-CN.md)。

借鉴 Dexter 的助理交互、FinRobot 的计算与证据约束、TradingAgents 的历史判断复查；参考 Fiscal.ai 的资料引用、PortfolioPilot 的持仓上下文、TradeZella 的理由与成交对照，以及 OpenBB 的工作台交互。

Milo 的重点是把这些能力围绕个人账户连起来，不需要复制机构终端、自动交易团队或日内交易日记。

## 4. V1.0 功能范围

### 4.1 持仓总览与问答

交付：
- 账户、持仓、现金、账本提供的盈亏及数据更新时间。
- 按账户、标的、资产类别查看配置；有可靠分类时展示行业集中度。
- 回答“我的主要风险集中在哪里”“这段时间哪些持仓贡献较大”等问题。
- 从持仓直接发起公司研究、查看历史报告和投资理由。

验收：
- 金额和比例来自确定性计算或 MCP 明确口径，保留账户范围、币种、统计区间和源数据版本。
- 未提供的字段不当作零；多币种无可靠汇率时分币种展示。
- 账本不支持持仓盈亏贡献时，明确缺口，不由模型推算成交或补造收益。
- 展示价格、账户同步和研究资料各自的时点，不能用一个“更新时间”代替所有来源。

### 4.2 公司研究与证据问答

交付：
- 围绕业务、财务变化、核心风险和待验证假设生成结构化研究。
- 支持公司资料、公开公告及可提取文本的财报 PDF；扫描件识别列入后续版本。
- 关键事实和数值可定位到原始资料段落、页面或结构化字段。
- 报告中区分已确认事实、分析判断、冲突信息和资料缺口。
- 支持对报告继续追问，沿用对应标的、财务期间及资料集合。

验收：
- 每个关键事实具有证据 ID；引用 ID 必须对应已获取的材料。
- 记录标题、机构、URL、发布日期、抓取时间、财务期间、原文位置和内容摘要。
- 公司同名、证券代码跨市场重复、财报期间不一致时先消歧或标注。
- 检索和模型执行有预算、轮次及超时限制，资料不足时返回带缺口的报告。
- 引用存在的程序检查与“原文是否支持断言”的人工评测分别记录。

### 4.3 两家公司对比（增强能力）

交付：
- 同一问题下对比最多两家公司，复用已有研究资料。
- 展示业务差异、财务指标、估值信息、风险和证据覆盖情况。
- 财务期间、币种或会计口径不可比时明确标记，不强制生成排名。

验收：
- 两侧来源、单位、统计期间可见；缺少数据的一侧不被模型补齐。
- 以对比问题和证据得出差异说明，不给缺少依据的综合分数。

### 4.4 投资档案与确认式记忆

交付：
- 每个标的记录投资理由、关键假设、风险、观察窗口及复查条件。
- 区分用户输入、用户确认内容和 Agent 草稿。
- 保存版本，关联当时的研究报告与资料集合。
- 可保存用户确认的偏好和约束，例如投资期限、关注方向、单一标的仓位上限。

验收：
- Agent 生成的新理由进入草稿，经用户确认才成为当前版本。
- 后续报告不能自动覆盖原判断；并发更新以版本号检查冲突。
- 聊天历史、研究事实和用户立场分别存储。历史模型判断不能因为被检索出来就升级为已确认事实。

### 4.5 仓位变化试算（增强能力）

交付：
- 用户输入假设买入/卖出数量或金额，计算预计持仓权重、现金变化及集中度变化。
- 显示价格时点、费用假设和币种，保存情景草稿以供比较。
- 按用户已确认的约束标出需要注意的变化。

验收：
- 计算由程序完成；使用过期价格或无法取得费用时明确标注假设。
- 情景与真实账本隔离，不写入真实成交，不调用下单接口。
- 仅描述指定操作对组合的影响，不把未来收益预测当作确定结果。

### 4.6 按需复盘与投资判断复查

两种入口：

**操作复盘**：选择一笔或一组成交，关联操作前后的快照、当时记录的理由及后续变化，回看是否符合原计划和约束。

**理由复查**：打开投资档案，选择“用新资料复查”，对照原假设整理支持证据、反证及尚无足够信息的部分。没有发生交易也可以使用。

报告内容：
1. 当时的决策与资料时点。
2. 实际成交或当前需要复查的假设。
3. 计划与实际的差异，以及有证据支持的变化。
4. 尚不能判断的部分、需要补充的资料。
5. 对原投资档案的修改建议；用户确认后生成新版本。

验收：
- 没有真实成交数据时，不根据持仓差额断言发生买卖。
- 没有当时理由时显示“未记录”；事后补记保留补记时间，不伪装为事前理由。
- “决策当时可知的信息”和“复查时新出现的信息”分开呈现。
- 没有当时快照或留存资料时标记历史证据缺失；当前检索结果不能包装为当时已知内容，仅有发布日期也不能证明当前修订版当时已存在。
- 盈亏表现与执行是否符合原计划分别描述；观察期不足时保留未决状态。
- 同一输入重复执行不会重复发布相同档案版本；输入更新时产生可追踪的新报告版本。

### 4.7 工作台与任务体验

页面：总览、研究、投资档案、复查记录、设置。对话作为跨页面入口；任务列表展示研究和复查的进度与结果。

交付：
- 长任务在后台运行，刷新或断线后可继续查看。
- 支持取消、重试、失败原因、资料缺口和报告导出为 Markdown。
- 展示阶段与工具结果摘要，不依赖展示模型隐藏推理过程。
- 界面按既定暖纸技术手册风实现，优先桌面研究体验并适配移动端阅读。

## 5. 核心 Agent 设计

采用 Mastra 主 Agent 路由明确的专业工作流。Mastra Workflows 组织固定步骤，步骤内的 Agent 负责需要模型规划与综合判断的部分：

| 工作流 / Skill | 主要职责 | 输出 |
| --- | --- | --- |
| portfolio-analysis | 读取账户范围、调用计算工具、解释变化与风险 | 持仓诊断 |
| company-research | 制定有限研究计划、检索材料、提取证据、组织判断 | 引用可追溯的研究报告 |
| company-comparison | 对齐对象与口径，比较已有资料 | 双公司对比 |
| thesis-review | 对照指定档案版本核查新证据 | 复查报告与修改提案 |
| trade-review | 关联真实成交、理由和后续数据 | 按需操作复盘 |

Skill 定义输入条件、允许工具、步骤、输出结构和完成条件，并保存版本。程序负责参数校验、权限、计算、引用 ID 校验和持久化；模型负责计划、选择资料、综合证据与文字解释。

Skill 是任务规范，Workflow 是执行流程，两者分别版本化。MCPClient 将经过筛选的账本工具接入 Agent；计算和报告发布通过有明确输入输出的业务工具执行。投资理由确认采用 Workflow 暂停与恢复，正式版本由 Milo 业务事务保存。

先做有限的专业工作流。多角色辩论、动态招募 Agent、任意代码执行不作为 V1 的验收条件。

## 6. 已确定的技术方案

2026-11-16 确定采用 **Next.js + TypeScript + Mastra + PostgreSQL**。选型依据、能力边界和验证步骤见 [ADR-001：采用 Mastra](ADR-001-MASTRA.zh-CN.md)。

| 层次 | 方案与职责 |
| --- | --- |
| 单仓库 | pnpm workspace，前端、Agent 服务、共享契约和评测同仓库 |
| Web | Next.js / React + Tailwind CSS v4；组件优先 Magic UI，其次 shadcn/ui。负责页面、访问控制、业务 API 与流式任务展示 |
| Agent 服务 | 常驻 Node.js 进程运行 Mastra，执行研究与复查，接入启动、恢复扫描和关闭生命周期 |
| 编排 | Mastra Agents + 基础 Workflows；固定步骤由工作流组织，开放式研究由步骤内 Agent 完成 |
| 工具 | Mastra MCPClient 连接投资记账本；自定义结构化工具封装财务计算、证据查询和受控写入 |
| 持久化 | PostgreSQL；Mastra PostgresStore 管理运行快照与对话，Drizzle 管理 Milo 业务表及迁移 |
| 记忆 | Mastra Memory 管理会话上下文；用户确认的投资理由、偏好和版本保存在 Milo 业务表 |
| 评测与调试 | Mastra Studio、Scorers 与执行追踪；结合确定性断言、人工来源核验和故障注入 |
| 契约与展示 | Zod、十进制计算库；框架流式事件配合业务持久事件序号，支持任务状态续读 |
| 部署 | Docker Compose 启动 Web、常驻 Agent 服务和 PostgreSQL |

框架运行表与 Milo 业务表分开命名或分 schema 管理，并分别维护迁移。业务 AgentRun 关联 Mastra runId，用于展示、权限和发布管理；步骤检查点由 Workflows 管理，不另写一套通用工作流引擎。

研究资料先按标的、期间和来源过滤，再进行段落检索。pgvector 语义检索保留为第 4 周的受控增强，由评测结果决定是否纳入发布。

V1 以基础 Workflows 为执行基线，配置 PostgreSQL 存储及运行进程的恢复机制。Durable Agents 的 beta 能力、外部执行平台和额外队列不作为首版前提；框架恢复也不能替代业务幂等、版本检查和原子发布。

正式投资理由不直接使用模型可更新的 working memory。用户确认、报告发布、财务口径和证据支持关系均属于 Milo 的业务实现。

官方依据：[Workflows](https://mastra.ai/docs/workflows/overview)、[暂停与恢复](https://mastra.ai/docs/workflows/suspend-and-resume)、[MCP](https://mastra.ai/docs/connections/mcp)、[PostgreSQL](https://mastra.ai/integrations/databases/postgresql)、[评测](https://mastra.ai/docs/evals/overview)。

## 7. 数据与恢复设计

核心对象：

| 对象 | 关键字段或关系 |
| --- | --- |
| AccountSnapshot | 来源、账户、数据时点、抓取时间、币种、覆盖范围、内容摘要 |
| Trade | 来源成交 ID、账户、证券标识、成交时间、数量、价格、费用；可缺失但不可推造 |
| SourceDocument / Evidence | URL、机构、发布时间、财务期间、内容摘要、原文位置、引用片段 |
| ResearchReport / Claim | 报告版本、断言、引用 ID、事实/判断/缺口分类、校验状态 |
| ThesisVersion / DecisionNote | 用户或模型来源、创建及确认时间、理由、假设、约束、关联证据与前一版本 |
| Scenario | 用户输入、价格快照、费用假设、计算结果，与真实账本隔离 |
| AgentRun / RunEvent | Mastra runId、类型、业务状态、输入版本、尝试次数、事件序号、预算与错误 |
| ReviewReport | 原档案/成交版本、当时资料、新资料、复查时点、差异与修改提案 |

研究和复查的业务状态如下；它们是 Milo 的展示与发布状态，不直接当作 Mastra 原生状态枚举。适配层将框架运行状态映射到业务状态，部分完成由业务校验结果决定：

~~~text
queued → running → succeeded / partial
                 → waiting_user
                 → failed / cancelled
~~~

- 由 Mastra Workflows 保存阶段执行快照，Milo 保存输入清单、业务产物与来源版本。恢复以已持久化的步骤为边界；尚未保存结果的步骤可能重跑。
- 持久化存储和恢复 workers 必须接入常驻服务生命周期；仅创建 Mastra 实例不能作为后台恢复已启用的证据。
- 幂等键包含用户与账户范围、工作流及版本、源快照、用户输入版本和参数摘要。相同输入可复用已完成结果或关联正在执行的运行。
- 失败或取消后主动重试创建新尝试记录，不能永久命中旧失败运行；产物发布使用独立唯一约束防止重复写入。
- 新资料或用户理由变化时创建新的输入版本，不静默覆盖历史报告。
- 框架恢复可能重新执行步骤。业务产物发布时原子检查当前尝试代次、取消状态和目标版本，拒绝已失效尝试的写入；不能假设框架租约已保护 Milo 业务表。
- 暂停确认绑定用户、runId、理由草稿版本和输入摘要；恢复前重新校验权限与版本，重复或过期确认不能生成多个正式版本。
- 每次请求关联执行 trace，记录模型/提示词/Skill/Workflow 版本、调用次数、token、耗时和费用估算口径。
- 用户私有账户和资料限定访问范围；公开演示与评测使用合成或明确脱敏的数据。

## 8. 八周开发计划

| 周 | 主交付 | 当周验收 |
| --- | --- | --- |
| W1 | 完成 Mastra 三项验证并锁定依赖；核验 MCP 与资料路径；搭建 Web、常驻 Agent 服务及数据库 | 真实账本只读；暂停后重启再确认；中断恢复且报告不重复；记录未通过项与缺失接口 |
| W2 | 持仓总览、账户快照与确定性计算、持仓问答 | 固定样本数值可核对；陈旧和缺失数据可见；从持仓发起任务 |
| W3 | 公司研究最小闭环、资料解析、证据与引用 | 两家公司可分别生成报告；点击关键事实能定位资料；失败有明确结果 |
| W4 | 双公司比较、报告追问、检索评测与质量校验 | 口径不一致可解释；资料不足可降级；决定语义检索是否值得保留 |
| W5 | 投资档案、理由版本、确认式记忆与仓位试算 | 用户确认后才更新理由；试算不污染真实账本；版本冲突可处理 |
| W6 | 按需操作复盘与理由复查、报告差异 | 完成“原理由→新证据→复查→用户确认更新”的演示；缺少理由不编造 |
| W7 | Mastra 追踪与 Scorers 集成；故障恢复、取消及业务幂等评测 | 刷新、断线、进程重启、工具超时后可恢复或给出明确失败；完成评测初稿 |
| W8 | 修复、部署、演示、使用文档与简历证据 | 可从干净环境启动；核心演示可重现；报告实测指标与限制，交付 V1.0 |

每周保留集成与修复时间；W7–W8 不再新增核心模块。若来源接入超出一周，按“可选语义检索 → 对比维度 → 仓位试算”的顺序裁减增强范围，保留持仓、研究、档案与按需复查四条核心能力。发布说明明确实际交付范围；调整评测范围时形成新版本，并记录裁减原因。

W1 的前三项验证安排约 1–2 个工作日，验收标准见 ADR-001。框架已经选定，验证用于锁定版本、配置和业务边界；未通过项应先定位，不能将文档支持直接写成运行验证通过。

## 9. 发布验收与评测

以下是计划中的验收方法及目标，不是已取得的成绩。

固定评测集建议 60 个案例，并记录版本、运行日期、模型和样本来源：
- 20 个持仓/仓位试算案例：包括现金流、币种、数据缺失、时间不齐和集中度。
- 12 个公司研究/对比案例：包含正常资料、冲突资料、过期资料和资料不足。
- 20 个档案/按需复查案例：包含事前理由、事后补记、无理由、观察期不足、版本冲突和重复请求。
- 8 个边界案例：包含外部资料中的指令注入、越权访问尝试和未注册工具调用。

另做 12 个故障注入场景，覆盖超时、限流、进程中断、重复请求和取消竞争。预留至少 20 个未参与提示词调试的案例作为留出集；调试集和留出集分别汇报。

| 指标 | 计算方式 | 发布目标 / 报告规则 |
| --- | --- | --- |
| 数值正确性 | 正确的受支持数值断言 / 全部受支持数值断言 | 固定计算样本全部正确；无法计算的案例单列，不以跳过掩盖错误 |
| 缺失与时点处理 | 正确标记的缺失/陈旧输入 / 全部对应案例 | 关键账本缺失必须可见，不编造交易或收益 |
| 引用可解析 | 能回到已获取证据的引用 / 全部生成引用 | 目标 100%；它只证明引用真实存在 |
| 证据支持度 | 人工判定受到来源支持的事实断言 / 抽检事实断言 | 每份研究抽 5 条关键断言，12 份共 60 条；目标至少 54/60，并记录争议项 |
| 判断版本正确性 | 正确保持/更新版本的场景 / 全部版本场景 | 未确认不得覆盖；历史理由及时间可追溯 |
| 恢复与幂等 | 可恢复/明确终止的故障场景与重复发布次数 | 分别报告结果；固定重复请求场景中重复发布为 0 |
| 延迟和成本 | 各任务端到端耗时、调用次数、token 和估算费用 | 分类型记录 N、中位数和 P95；标记缓存条件，实测后再制定性能承诺 |
| 端到端完成率 | 符合验收条件的完整任务 / 全部计划执行任务 | 完成、部分完成、失败分别计数，不能混为成功率 |

评测不以投资收益证明系统质量，也不把模型自评分当作引用真实性的唯一依据。

## 10. 发布演示

1. **我的持仓主要集中在哪里？** 选择账户范围，检查时间与币种，查看计算结果及对应账本快照。
2. **这家公司的关键变化是什么？** 从持仓发起研究并打开来源；缺失和冲突资料可见。双公司对比作为增强演示。
3. **我当初的投资理由还成立吗？** 选择已确认档案，引入新资料，生成复查与修改提案，用户确认后更新；中途刷新或重启仍能继续查看。

增强演示：**如果按这个金额调整，组合会怎样变化？** 用户指定假设金额，展示新的配置和现金，保持真实账本不变。该演示只在仓位试算实际交付时列入发布材料。

2. 一个首发研究市场，以及该市场的公告/财报/价格来源与额度。资料不可稳定取得时缩小标的清单。
3. Mastra 与 Node.js 的具体版本、存储适配器兼容性、模型、部署环境、许可证与调用预算。
